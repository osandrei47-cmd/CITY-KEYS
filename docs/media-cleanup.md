# Статус объекта и безопасное удаление — как это устроено

Памятка для не-разработчика: что реально происходит при смене статуса
объекта и как безопасно удалить объект, когда он больше не нужен, не
оставляя мусора в S3-хранилище.

## 1. Что происходит при смене статуса

Поле «Статус» в объекте (В продаже / Забронирован / Продан / сдан) — это
просто текстовое значение в самой записи. Никакой автоматической
архивации нет: объект **никуда не переносится**, остаётся той же записью
в той же таблице базы данных, что и был. Но некоторые страницы и фиды
сами решают, показывать ли объект, в зависимости от этого значения — и
делают это по-разному:

| Статус         | Каталог `/katalog`, главная, `/zhk/[slug]`, `sitemap.xml` | Страница объекта по прямой ссылке | Фиды Авито/ЦИАН/Яндекс/Домклик |
| --------------- | :-: | :-: | :-: |
| В продаже       | ✅ показывается | ✅ | ✅ уходит в фид |
| Забронирован    | ✅ показывается (с бейджем «Забронирован») | ✅ | ❌ **пропадает из фида** |
| Продан / сдан   | ❌ скрывается | ✅ | ❌ пропадает из фида |

Важные детали:

- **Фиды строже каталога.** Из фидов пропадает не только «Продан», но и
  «Забронирован» — как только вы ставите объект в бронь, площадки
  перестают его получать при следующей же выгрузке (фиды формируются «на
  лету» при каждом скачивании площадкой, без задержки и без отдельного
  редеплоя). Логика — `src/lib/feed/helpers.ts`, `activeListingsWhere`.
- **Каталог мягче.** Из каталога/главной/sitemap пропадает только
  «Продан» — «Забронирован» остаётся виден с пометкой. Логика —
  `status: { not_equals: "sold" }` в соответствующих страницах.
- **Страница объекта не скрывается никогда сама по себе.** Если у вас
  где-то сохранена прямая ссылка на проданный объект — она откроется, там
  просто будет написано «Продан / сдан» в характеристиках. Это осознанно
  (не 404 на старые ссылки), но имейте в виду.

## 2. Удаление объекта — что удаляется, а что нет

**Короткий ответ: удаление объекта (Listing) НЕ удаляет привязанные к
нему фото и видео.** Они остаются в коллекции Media и продолжают
занимать место в S3 — «осиротевшими», без единой ссылки на них.

Зато при удалении самого файла из коллекции **Media** — он гарантированно
удаляется и из S3 тоже, автоматически, это делает сам плагин хранилища
(`@payloadcms/storage-s3`), сразу же по факту удаления.

Отсюда правило: **чтобы удалить объект без мусора, надо удалить его самого
и его медиафайлы отдельно.**

### Как это сделать на практике

**Вариант А — вручную, для одного объекта (надёжнее):**

1. Откройте объект в админке, посмотрите список файлов в полях
   «Фотографии» и «Видео» — запомните имена файлов или откройте их по
   очереди.
2. Удалите сам объект (Listing).
3. Зайдите в `/staff-x7k2/collections/media`, найдите те же файлы (по
   имени, они не переименовываются) и удалите каждый — они уйдут из S3
   сами.

**Вариант Б — списком, если вы уже удалили несколько объектов и не
помните, какие файлы к ним относились:**

В проекте есть скрипт `scripts/find-orphaned-media.ts` — он **только
показывает** список файлов Media, на которые нигде нет ссылки (ни у
одного объекта, ЖК, проекта или статьи блога), и **ничего не удаляет
сам**, пока вы явно не попросите:

```
# из папки web/ — сначала просто посмотреть список (не удаляет ничего):
npx tsx scripts/find-orphaned-media.ts

# вывод покажет id/имя/размер каждого файла-кандидата и готовую команду
# для удаления — скопируйте её как есть, либо уберите из списка id тех
# файлов, которые хотите оставить:
npx tsx scripts/find-orphaned-media.ts --delete 230,229,228,...
```

По умолчанию скрипт смотрит **прод** (если рядом лежит `.env.prod.local`)
— то есть реальные боевые данные, а не тестовую базу. Явно можно
попросить dev: `npx tsx scripts/find-orphaned-media.ts .env.local`.

**Перед удалением по списку — проверяйте глазами.** Скрипт видит только
файлы, привязанные через обычные поля (фото/видео объекта, обложки ЖК и
проектов, обложка статьи блога). Он **не видит** файлы, на которые код
ссылается по-другому — например, скан свидетельства о товарном знаке на
`/o-kompanii` подключается по имени файла, а не по связи в базе; такой
файл скрипт уже умеет узнавать и исключает из списка сам (см. список
`FILENAME_LOOKUPS_IN_CODE` в начале скрипта), но если появится ещё один
похожий случай в будущем — его тоже нужно будет туда дописать. Если
сомневаетесь в каком-то файле — откройте его id в браузере
(`/staff-x7k2/collections/media/<id>`) и посмотрите, что это, прежде чем
удалять.

При первом запуске (24 сентября 2026) скрипт нашёл **75 файлов, 387 МБ**
без единой ссылки — то есть примерно треть всех файлов в Media вообще ни
к чему не привязана. Похоже, это копится давно (не разовая история), и
имеет смысл прогонять скрипт время от времени, а не только при удалении
конкретного объекта.

## 3. Где посмотреть, сколько места занято в S3

Диск, который вы уже смотрели в панели Timeweb — это диск самого
приложения (кода сайта), он с медиафайлами никак не связан: все фото,
видео и PDF лежат в **отдельном облачном S3-хранилище** (бакет
`city-keys-media`, эндпоинт `s3.twcstorage.ru`).

Смотреть его занятость нужно в другом разделе личного кабинета Timeweb —
там, где перечислены облачные (S3-совместимые) хранилища, а не серверы
или диски приложений; внутри бакета `city-keys-media` обычно виден общий
занятый объём и можно открыть список файлов/папок. Я не захожу в ваш
личный кабинет Timeweb напрямую, поэтому не могу дать точное название
пункта меню и скриншот — если раздел называется иначе, чем ожидаете,
поищите по словам «хранилище», «S3» или «объектное хранилище» в общем
меню кабинета.

Важно: в этом же бакете, но вне коллекции Media (и поэтому не видны ни в
admin-панели Payload, ни в выводе `find-orphaned-media.ts`), лежат ещё
презентационные PDF и видео проектов/ЖК — под путями `private/zhk/...`
и `videos/...`. Их скрипт не проверяет и не трогает: они не документы
Media, а их значимость в общий объём S3 всё равно входит.
